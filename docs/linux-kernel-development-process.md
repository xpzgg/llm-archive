# Linux 内核开发流程图（补丁流水线 + 版本演进）

```text
═══════════════ 补丁流水线（任何时间，feature / bugfix 均可）═══════════════

 ① 邮件列表评审            ② maintainer 树              ③ linux-next
    git send-email     →    各子系统自己的树         →    所有 maintainer 树
    投稿，评审→修改→        （akpm -mm / tip /           的每日合集，
    v2/v3 ... 直到收下       netdev / btrfs ...）        做集成测试
                               │ 收下后可随时            （规则：merge window
                               ▼ fixup / 更新             开启前就应泡在这里）
────────────────────────────────────────────────────────────┼──────────────
                                                            ▼
                                          ④ merge window：汇入主线
                                             feature 的唯一入口
──────────────────────────────────────────────────────────────────────────────

══════════════════════ 版本演进（时间 →）══════════════════════

 |<----------------- N 开发周期 ---------------->|<-------- N+1 周期 -------
 ┌─────────┐┌─────┬─────┬────┬──────┬──────┐┌─────────┐
 │ merge   ││ rc1 │ rc2 │... │rc7/8 │  N   ││ merge   │ → 循环
 │ window  │└─────┴─────┴────┴──────┴──────┘│ window  │
 └─────────┘                                └─────────┘
   ~2 周       ~6~10 周：rc 阶段只收 bugfix
               （maintainer 每周发 fix pull，
                 rc 越靠后审查越严）
                                   │
                                   ▼
                    ⑤ 正式版发布后：stable 树
                       带 Cc: stable 的 fix
                       被回合到各旧版本
```

## 读法

1. **流水线随时转**：①②③ 没有时间窗口，feature 和 bugfix 都走同一条路；大部分补丁是在上一个周期的 rc 阶段走完这段的——N 的 rc 期就是 N+1 补丁的准备期，两排齿轮咬合着转。
2. **feature 只有一个入口**：merge window（④）。错过就等下一轮，所以 maintainer 都在窗口早期发 pull request，压轴大 feature 会被 Linus 拒。
3. **bugfix 有两个入口**：merge window 随批次进，或 rc 阶段随每周的 fix pull 进；但 rc 越晚门槛越高，后期基本只收小修和 regression fix。
4. **正式发布后**：带 `Cc: stable` 的 fix 由 stable 团队回合到各旧版本（⑤），这就是 6.x.y 点版本的来源。

规模参考（出自 `Documentation/process/2.Process.rst`）：每个版本约 1.3 万个 changeset，merge window 期间以接近每天 1000 个的速度合入。
