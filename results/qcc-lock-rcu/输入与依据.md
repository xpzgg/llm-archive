# 工具输入与排查依据

这份清单把四页中的疑因转成后续工具要接收的材料。当前归档的是设计输入，尚未实现 Agent 工具，也没有实测提效数字。可复制[输入模板](agent-inputs.example.json)填写；`null` 表示未知或未提供，工具应返回相应缺项和可继续完成的检查。

## 四类工具需要什么

| 工具与疑因 | 需要的输入 | 应交付的结果 |
|---|---|---|
| 现场包检查 F5 | vmcore、匹配的 vmlinux/模块符号、构建信息、实际现场镜像与固件版本、dump 采集记录 | 版本核对、关键对象读取结果、缺项及影响范围；过滤掉无关页不等同于 dump 不可用 |
| vmcore 分析 F1/F2 | 上述可用现场；相关内核版本的类型信息；完整 stall 日志；RCU trace 有则补充 | CPU/任务栈、相关锁地址和等待关系、RCU GP/CPU/阻塞任务状态，以及命令和内存地址；未完成项单列 |
| 平台联查 F3/F4 | CPU/内存/互联频率、系统计数器频率、ESL 计时模式与时序精度、IRQ/负载进度、串口、互联或仿真 trace、寄存器定义版本 | 按共同事件对照软件和平台观察，列明需芯片侧确认的 CPU、地址、事务或 IRQ；保留无法对齐的时间段 |
| 定向复现 F6 | 当前假设、原脚本、镜像/bitstream/固件版本、负载/绑核参数、平台采证限制 | 一轮具体实验：观察点、预期结果、采集范围、停止条件；由测试与平台人员审核执行 |

`incident_kernel_config_path` 指故障现场的内核配置，不能用分析工作区的 `.config` 代替。不同来源的时间戳需要保留时钟单位、起点和事件对应关系；ESL 仿真时间、guest 时间、host 墙钟时间不能直接当成同一条时间轴。

## vmcore 分析值得先试在哪里

把固定检查封装成脚本：批量取 CPU/任务栈，查相关对象，按版本解析锁和 RCU 状态，再由 Agent 根据结果决定下一步查询并查对应代码。复核者能回到具体命令和地址，检查结论是否站得住。原始 dump 留在分析机，Agent 使用查询结果及必要上下文。

`crash` 已有 [`bt -a`](https://crash-utility.github.io/help_pages/bt.html)、[`foreach bt`](https://crash-utility.github.io/help_pages/foreach.html) 和 [`runq`](https://crash-utility.github.io/help_pages/runq.html) 等批量检查入口；[drgn locking helpers](https://drgn.readthedocs.io/en/latest/helpers.html#locking) 提供 `mutex_owner` 等对象查询。这些工具能力支撑“减少重复查询”的实现思路，不能证明 Agent 已经比人工快。

仓库中的 [qspinlock MCS 排查笔记](../qspinlock_mcs_walk.md)和 [RCU GP 解析脚本](../../scripts/parse_rcu_gp.py)可作封装起点。需按故障内核核对字段、锁实现和 trace 格式：qspinlock 的 tail 是队尾等锁者，不能当成持锁者；trace 没记录某个事件，也不能推出它从未发生。

先用已结单旧案例隐藏答案后试用，固定检查清单，记录加载、执行、复核、补查的总工时与错误/漏项。参与者不应先用人工看过同一案答案，再把熟悉后的 Agent 耗时拿来比较。离线分析的提速另记，问题受理到根因确认的总时长仍保留平台运行和协同等待。

## 公开资料说明了哪些排查分支

| 资料 | 支持的判断 | 使用范围 |
|---|---|---|
| [Linux RCU stall 文档](https://www.kernel.org/doc/html/latest/RCU/stallwarn.html) | stall 可能涉及 RCU 读侧、调度、定时器、中断、慢系统或调试开销；需要结合连续现场判断 | 解释机制；具体字段以目标内核版本为准 |
| [Arm64 启动约定](https://docs.kernel.org/arch/arm64/booting.html) | 系统计数器频率与跨 CPU 计时设置有明确要求 | CPU 主频与系统计数器频率分别核对，不按主频比例直接改超时 |
| [Arm Fast Models 11.22 用户指南，p.25](https://documentation-service.arm.com/static/648c77ea153eb247a5450e70) | PV 模型的功能准确性与硬件时序准确性有区别 | 这是特定模型示例；用户的 ESL 模型能力须查自身说明 |
| [Arm CI-700 勘误 3031700，p.23](https://documentation-service.arm.com/static/683d2ddc771bba091ac6f76f?token=) | 特定互联条件下确有死锁机制 | 仅作公开机制实例，不能套用为本平台的故障结论 |
| [crash 使用说明](https://crash-utility.github.io/crash_whitepaper.html) | dump 分析需要匹配的符号与构建信息 | 先检查材料能否支撑目标对象的读取 |
| [Linux kdump 文档](https://docs.kernel.org/admin-guide/kdump/kdump.html) | vmcore 保存系统内存现场，可按条件过滤 | 本方案据此限定：未记录的历史事件与互联事务还需其他证据 |

来源检索日期：2026-11-05。QCC 的要因确认与对策方法沿用 [T/CAQ 10201—2024](https://www.panyu.gov.cn/attachment/7/7835/7835136/10324082.pdf)的调查分析及 5W1H；实际主要原因仍按案例中的耗时贡献确定。
