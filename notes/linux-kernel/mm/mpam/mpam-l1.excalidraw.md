④ 代价 ^s4head01

• 标签数量有限：能建多少组，受芯片 PARTID / PMG 的位数限制
• 只有接入了标签的节点才能管：哪些节点支持、支持哪些控制，因芯片而异
• 擅长限制上限；带宽下限只是优先级提示，不是硬保证
• 配额要自己定：给多少合适，得靠计数数据反复调 ^s4text01

附：放到更大的图景里 ^s5head01

• x86 上的同类机制是 Intel RDT：CLOSID 对应 PARTID，RMID 对应 PARTID + PMG
• 区别：MPAM 把标签做进总线请求，任何厂商的 cache、内存控制器、SMMU 都能接入
• Linux 入口是 resctrl 文件系统（x86 与 Arm 共用）：建目录就是建组，schemata 写配额
• 和 SMMU 的对应：SMMU 按 StreamID 查翻译表，MSC 按 PARTID 查配额表
• AI Infra：推理与训练、数据预处理混部时，给推理保 L3，给离线任务限带宽
• 芯片对接：内核只按 BIOS 的 ACPI MPAM 表认识 MSC；HHA 上的 MSC 支持哪些控制，
   以芯片规格和 BIOS 为准（本图未在代码中核实） ^s5text01

D  不同部件怎么执行配额和计数 ^hwDh0001

cache（L2、L3） ^hwDch001

• 按份限额（CPBM）：cache 被切成若干份，常见实现是按“路”切。
   请求未命中、要换入新数据时，只能在本 PARTID 的那几份里挑一行替换；
   命中不受限，共享的数据照样能读到
• 容量上限（CMAX）：按比例限制一个 PARTID 最多占多少
• 占用统计（CSU）：要知道每一行属于谁，cache 行旁边得多存几位标签，
   这是额外的面积成本 ^hwDct001

内存带宽（内存控制器一侧） ^hwDbh001

• 在一个统计窗口（MBW_WINWD）里累计每个 PARTID 用掉的带宽
• 超过上限（MBW_MAX）：降低它的优先级；HARDLIM 置位则直接压住
• 低于下限（MBW_MIN）：提高优先级，尽量先满足它
• 流量统计（MBWU）：按 PARTID / PMG 累计流过的字节数 ^hwDbt001

E  硬件代价，以及软件怎么接上 ^hwEh0001

• 标签要占硬件：每个请求多带 PARTID + PMG 字段，每个 cache 行多存标签
• 配置表有多少行，就最多支持多少个 PARTID，所以 PARTID 数量有限
• 缓解办法是 Narrow PARTID：MSC 内部只存少量配置（intPARTID），多个请求标签（reqPARTID）
   映射到同一份配置。OLK-6.6 借此在不增加配置表的情况下扩出更多监控组 ^hwEtx001

软件接上硬件的路径：BIOS 的 ACPI MPAM 表列出所有 MSC → 驱动读各 MSC 的能力寄存器
→ resctrl 把能力导出为 L2 / L3 / MB 等资源 → 你在主图 ❶ 里写下的配额 ^hwEsw001

③ 监控器：每个 MSC 固定几个（这里 4 个）
每个 = 过滤条件 + 计数寄存器

G  这次讨论里澄清的问题 ^hwGh0001

• PARTID 管配额，PMG 只管计数。配额按整个 PARTID 算，同组各 PMG 共用、会互相挤；要隔离就分不同 PARTID
• 配额只在未命中、要放进新数据时起作用；命中就直接读，读哪一份都行
• 按份划分只决定“能放在哪几份”，满了按 cache 原有替换策略在这几份里换出；容量上限、带宽上限则要统计用量
• PARTID 贵：每个 MSC 都要为每个 PARTID 存一行配置，每次分配都要查；PMG 便宜：只多几位标签，不需要配置表
• 监控组是软件概念（PARTID + PMG 的组合，最多 PARTID 数 × PMG 数个）；监控器是硬件，每个 MSC 固定几个，
   决定同一时刻能真正计数的组有几个
• 组比监控器多时（OLK-6.6）：读数时驱动按 PARTID 取余选监控器，必要时改过滤条件。占用要等“就绪”再读；
   带宽从 0 重新计数，切换之前的流量就丢了
• 带宽计数是累计字节：带宽 = 两次读数之差 ÷ 时间差。计数器有 31 / 44 / 63 位，会溢出：硬件置溢出位，驱动补一圈，
   resctrl 每 1000 ms 读一次；两次读之间溢出不止一圈就不准，所以高带宽要用长计数器
• 为什么这几年才普及：混部和多核共享 L3 让问题变尖锐；硬件要整条路径的部件配合，Arm 生态得先有统一规范；
   软件上 resctrl 原本为 x86 写，要先改成通用框架 ^hwGtx001
