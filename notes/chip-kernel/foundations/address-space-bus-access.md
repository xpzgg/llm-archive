# 地址空间与总线访问（L1）

> 等级：L1 概念与设计，不涉及内核代码。以 Arm64 为主。
> 依据见文末。文中的地址数值都是示意，每个平台不同。

读完要能回答三个问题：

1. CPU 执行一次读或写，凭什么送到内存或某个设备，中间经过哪几层？
2. 同样是"按地址读写"，为什么访问设备不能像访问内存那样被缓存、合并、重排、提前执行？
3. 一条写指令执行完了，设备就收到了吗？什么时候必须确认它已经到达？

## 1. 把设备寄存器当成内存来访问，会出什么事

CPU 和外部打交道只有一种动作：给出一个地址，读或者写几个字节。内存是这样访问的，设备也是这样访问的。设备把自己的控制接口做成一组**寄存器**，每个寄存器占一个地址，软件读写这些地址就是在操作设备。

拿串口举例。它有两个寄存器：

- **状态寄存器**：其中一位表示"收到了一个字节，还没被取走"。
- **数据寄存器**：读它，取走收到的那个字节；写它，把一个字节发送出去。

收一个字节的程序很简单：反复读状态寄存器，直到那一位变成 1，然后读数据寄存器。

现在假设 CPU 不知道这两个地址后面是设备，按访问内存的方式来执行这段程序。CPU 为了让内存访问更快做了几种优化，每一种都会让这段程序出错：

| CPU 对内存访问做的优化 | 这段程序会怎样 |
|---|---|
| 缓存：读过的数据留在 cache 里，再读同一个地址直接用 cache 里的 | 第一次读状态寄存器得到 0，之后每次读拿到的都是 cache 里的 0。串口早就收到数据了，程序永远等不到。 |
| 提前读：分支结果还没算出来，先按猜测把后面的数据读回来，猜错就丢掉 | CPU 猜"状态位是 1"，提前读了数据寄存器。结果猜错了，读回的数据被丢掉，但串口那边已经把这个字节当作"被取走"了。这个字节丢了。 |
| 重复：一次读被中断打断，回来后重新读一遍 | 数据寄存器被读了两次，取走了两个字节，程序只拿到后一个。 |

发送也一样。连续向数据寄存器写两个字节，再加上"先写配置寄存器，再写启动寄存器"这种常见操作，又有两种优化会出事：

| CPU 对内存访问做的优化 | 会怎样 |
|---|---|
| 合并：对同一个地址连续写两次，只把最后一次真正写出去 | 两个字节只发出去一个。 |
| 重排：后执行的访问先到达 | 启动命令先到，设备按旧配置开始工作。 |

这些优化对内存都是对的，因为内存只是存数据：读它不会改变它，读多少次结果都一样，写进去什么读出来就是什么。设备寄存器不满足这几条，读写它本身就是在让设备做事。

所以硬件和软件之间必须约定好三件事，这也是后面四节的内容：

- 一个地址后面到底是内存还是设备，是哪个设备（第 2 节）。
- CPU 怎么知道某个地址是设备，知道以后关掉哪些优化（第 3 节）。
- 优化关掉以后，还有什么是硬件保证不了、要软件自己处理的（第 4、5 节）。

## 2. 一个地址后面是内存还是设备，由谁决定

CPU 核向外发出的地址叫**物理地址**。全部物理地址构成物理地址空间，它像一张地图：一部分地址分给内存，一部分分给各个设备的寄存器，还有一些没人用。

一个示意的布局：

```
物理地址
0x0000_0000 ┌──────────────────────┐
            │ 启动 ROM              │
0x0800_0000 ├──────────────────────┤
            │ 片上设备的寄存器       │  中断控制器、串口、定时器……
0x1000_0000 ├──────────────────────┤
            │ （没人用）            │
0x2000_0000 ├──────────────────────┤
            │ PCIe 窗口             │  分给插在主板上的设备：网卡、GPU、NVMe 盘
0x4000_0000 ├──────────────────────┤
            │ 内存                  │
            └──────────────────────┘
```

Linux 上 `/proc/iomem` 显示的就是本机的这张图。

软件把设备寄存器放进物理地址空间、用普通读写指令访问的做法，叫 **MMIO**（Memory-Mapped I/O）。

这张图不是存在某个地方的一张表，它是由硬件的连接方式实现的，分两级。

**第一级在芯片内部，设计芯片时就定死了。** CPU 核、内存控制器和各个片上设备由一组总线连在一起，这组总线叫**片上互连**。CPU 发出一次访问，互连看它的物理地址落在哪个范围，就把它转给对应的设备。这个动作叫**地址译码**。哪段地址归谁是做在电路里的，软件改不了。操作系统靠固件提供的硬件描述（设备树或 ACPI 表）得知这张图。

**第二级在 PCIe 上，由软件分配。** PCIe 是连接主板上外部设备的总线。片上互连和 PCIe 之间有一个转换器，叫**主桥**。主桥在物理地址空间里占一大段窗口，落在窗口里的访问都交给它，它再转成 PCIe 上的报文发出去。窗口内部怎么切给各个 PCIe 设备，由固件或内核在开机扫描设备时决定：给每个设备分一段地址，写进这个设备的 **BAR**（Base Address Register，基地址寄存器）。此后设备只认领地址落在自己 BAR 范围内的报文。

对着图看：中间那一条竖着的色带就是这张地图，也就是片上互连的译码；右边是每一段地址通向的东西。

## 3. CPU 怎么知道这段地址是设备

CPU 核是通用的。它不知道自己被装进了哪颗芯片，也不知道哪段地址后面接了什么。知道地图的是软件。所以只能由软件告诉 CPU。

告诉的途径是页表。程序用的是虚拟地址，CPU 里的 MMU（Memory Management Unit，内存管理单元）每次访问都要查页表，把虚拟地址换成物理地址。页表的每一项除了物理地址，还带一个**内存类型**。软件映射一段地址时，同时声明它是哪种类型；CPU 查页表时顺便拿到类型，按类型决定怎么访问。

Arm 的内存类型分两大类：

- **Normal**：普通内存。第 1 节的五种优化都允许。
- **Device**：设备。访问不经过 cache；指令确定要执行了才发出访问，不提前读；一次访问在总线上只发生一次。这三条是固定的，对应第 1 节的缓存、提前读、重复。

剩下的合并和重排，Device 类型用两个开关分别控制，另外还有第三个开关管写操作的应答：

| 开关 | 打开它表示允许什么 | 关掉它，得到什么保证 |
|---|---|---|
| G（Gathering） | 把多次访问合并成一次 | 程序里访问几次、每次多宽，总线上就是几次、多宽 |
| R（Reordering） | 改变访问的先后 | 对同一个设备的访问，按程序里的顺序到达 |
| E（Early Write Acknowledgement） | 写操作由途中的某一环节代替设备回答"收到了" | "收到了"必须由最终的设备回答 |

类型的名字就是三个开关的状态，关掉的前面加 n。例如 **Device-nGnRE** 表示不合并、不重排、允许途中代答，这是 Linux 映射设备寄存器时默认用的类型。为什么默认允许途中代答，要到第 5 节才能说清楚。

两点补充：

- R 关掉以后保证的只是**同一个设备内部**的顺序。对两个不同设备的访问之间，或者设备访问和内存访问之间谁先谁后，它不管。那要靠内存屏障，是路线图第 2 项的内容。
- MMU 还没打开时没有页表可查。Arm 规定这时所有数据访问都按最严格的 Device 类型处理。这样访问设备一定安全，但访问内存很慢，所以启动代码会尽早打开 MMU。

## 4. 一次读写怎么从 CPU 走到设备

用一个具体的例子走一遍。沿用第 2 节的地图，假设：

- 主桥的窗口是 `0x2000_0000` 到 `0x3FFF_FFFF`。
- 开机时内核给一块网卡分了 `0x2010_0000` 起的 64 KB，写进了网卡的 BAR。
- 驱动要向网卡偏移 `0x18` 处的控制寄存器写入数值 1，也就是写物理地址 `0x2010_0018`。
- 驱动事先已经把这 64 KB 映射好，页表里的类型是 Device-nGnRE。

### 写

1. **查页表。** CPU 执行写指令，MMU 查页表，得到物理地址 `0x2010_0018` 和类型 Device-nGnRE。
2. **按 Device 的规矩发出。** 这条指令确定要执行之后，CPU 不查 cache，不和别的访问合并，按程序里的顺序把一次 4 字节的写发上片上互连。
3. **译码。** 互连看到 `0x2010_0018` 落在 `0x2000_0000` 到 `0x3FFF_FFFF` 之间，转给主桥。
4. **主桥应答。** 主桥收下这次写，在片上互连上回答"写完成"。对 CPU 来说，这次写到此结束。
5. **变成报文。** 主桥把它打包成一个 PCIe 的"内存写"报文：地址 `0x2010_0018`，数据 1。
6. **转发。** 主桥和网卡之间可能隔着几级 PCIe 桥。每一级桥记着自己下游各个端口负责的地址范围，把报文转给范围包含 `0x2010_0018` 的那个端口。
7. **到达。** 网卡看到地址在自己的 BAR 范围内，收下报文，更新控制寄存器，开始做相应的事。PCIe 的内存写报文没有回复，流程到这里结束。

如果目标是片上设备（比如串口），走到第 3 步互连就直接转给设备，设备收下后应答，没有后面的报文和转发。

注意第 4 步和第 7 步：CPU 得到"写完成"时，报文可能还在路上。第 5 节专门讲这件事。

### 读

读同一个寄存器，前三步相同。之后：

- 主桥发出"内存读"报文，然后等着。
- 网卡收到后，发回一个带着数据的"完成"报文。
- 主桥拿到数据，才在片上互连上应答。CPU 的读指令一直等到这时才结束。

读必须拿到数据，所以路上每一级都得等到底。因此读比写慢；读指令结束时，可以确定设备已经处理过这次读。

### 地址后面没有设备

把例子里的地址换成一个没人认领的地址，结果取决于是哪一级发现没人认领。

**互连发现的**（比如访问了地图里"没人用"的那一段）：互连回一个错误应答，CPU 收到后产生异常。

- 如果能对应到具体是哪条指令，产生的是同步异常，内核知道是谁干的。读通常是这种。
- 如果对应不到，产生的是 **SError**（System Error）。它是一种异步异常，到来时出错的指令早已执行完，内核不知道是谁干的，通常只能 panic。写经常是这种。

哪种访问产生哪种异常，由芯片的实现决定。

**PCIe 上发现的**（地址在主桥的窗口里，但没有设备的 BAR 包含它，或者设备已经被拔掉）：

- 读：主桥等不到正常的完成报文。传统做法是主桥自己造一个全 1 的数据还给 CPU，所以驱动读到 `0xFFFFFFFF` 常常意味着设备不在了。有的 Arm 平台的主桥改成向 CPU 报错，产生异常。
- 写：报文被丢掉，CPU 这边没有任何感觉，只在 PCIe 的错误记录里留下一条。

## 5. 写指令执行完了，设备收到了吗

不一定。一次写从指令到设备，路上有三个地方会让上游认为"已经完成"，图的下半部分画的就是这三处：

1. **CPU 核内部。** 写指令执行完，数据先放进核内的写缓冲，之后才发上总线。
2. **主桥。** 上一节第 4 步：主桥收下就应答，这时报文还没发出去。这就是第 3 节 E 开关所说的"途中代答"。
3. **PCIe。** 内存写报文发出去就算完，没有回复。这种不等回复的写叫 **posted write**。PCIe 上只有内存写是这样；读，以及对设备配置信息的读写，都要等回复。

这样设计是为了快。写不需要带回数据，如果每次都等设备回话，总线的吞吐会低很多。

现在可以回答第 3 节留下的问题。PCIe 的内存写没有回复，所以"写完成必须由最终的设备回答"在 PCIe 上做不到，主桥只能代答。Linux 默认用允许代答的 Device-nGnRE，并且要求驱动一律按"写可能还没到"来写，这样同一份驱动在所有总线上都正确。

### 这会造成什么问题

写指令返回了，软件不能假设设备已经收到。三种典型的出错方式：

- **关中断后马上拆除处理函数。** 驱动向设备写"关闭中断"，接着释放中断处理要用的数据。写还在路上，设备又发来一个中断，处理函数访问了已经释放的数据。
- **复位后计时。** 驱动向设备写复位位，然后按手册等 10 ms。这 10 ms 是从 CPU 写完开始算的，设备实际收到复位更晚，得到的复位时间不足 10 ms。
- **写出错找不到是谁。** 写出错时指令早已执行完。这就是上一节里写出错常常变成 SError 的原因。

### 怎么确认写已经到达

写完之后，读一次同一个设备的某个寄存器（选一个读了不会改变设备状态的）。

这样做有效，靠的是前面已经出现过的两条事实：读要等设备回数据才结束；发往同一个设备的读不会越过它前面的写。读回来了，前面的写就一定到了。

代价是多一次完整的往返。所以只在先后顺序要紧的地方这样做：关中断、复位、掉电之前。平常的寄存器写晚到一点没有影响，不需要确认。

## 6. 还有一类寄存器不走地址：系统寄存器

前面讲的都是"按地址访问"。CPU 还有一类寄存器不按地址访问，叫**系统寄存器**。它们在 CPU 核内部，控制核自己的行为：MMU 开没开、页表在哪、当前屏蔽了哪些中断。第 3 节说的"软件声明内存类型"，最终也落在一个系统寄存器上。

访问它用专门的指令（Arm 上读用 `MRS`，写用 `MSR`），要访问哪个寄存器直接写在指令里。访问在核内完成，不查页表，不经过 cache，不上总线。图里 CPU 核内最上面那一行画的就是它。

和 MMIO 寄存器对比：

| | MMIO 寄存器 | 系统寄存器 |
|---|---|---|
| 在哪 | 设备里 | CPU 核里 |
| 怎么指定 | 地址 | 名字，写在指令里 |
| 有几份 | 每个设备一份，所有核看到的是同一个 | 每个核各有一份 |
| 谁能访问 | 页表映射了就能访问 | 看 CPU 当前的特权级 |
| 访问有多快 | 每次都走一趟总线 | 在核内完成，快得多 |

由"每个核各有一份"可以推出一条实用的结论：在核 0 上写了一个系统寄存器，核 1 上的同名寄存器不变。一项配置要全系统生效，必须在每个核上各写一次，包括之后才上线的核。

一个硬件特性常常两类寄存器都用：做在每个核里的部分用系统寄存器，全系统共享的部分用 MMIO。

- GICv3（Arm 的中断控制器）：每个核认领中断、结束中断用系统寄存器，因为这些操作极其频繁；负责把中断分给各个核的全局模块用 MMIO。
- MPAM（Arm 的 cache 和内存带宽划分特性）：给当前运行的任务打标签用系统寄存器，切换任务时改；配置各级 cache 按标签怎么分配用 MMIO。

遇到一个新特性，先分清它的寄存器哪些是系统寄存器、哪些是 MMIO，就知道哪些配置要在每个核上做、哪些全局做一次。

## 7. 这样设计付出了什么

| 得到了什么 | 付出了什么 | 怎么缓解 |
|---|---|---|
| 设备访问的次数、宽度、顺序和程序写的一致 | 每次访问都走一趟总线，不能缓存，不能提前执行，比访问内存慢得多 | 少碰寄存器。大量数据放在内存里，只用一次寄存器写通知设备来取（路线图第 12 项） |
| 写不等设备回话，总线吞吐高 | 写什么时候到达不确定，出错难以找到是哪条指令 | 在顺序要紧的地方写后读一次，代价是一次往返 |
| 系统寄存器访问快 | 每个核一份，配置要在每个核上各做一遍，核上线、下线都要处理 | 内核有统一的每核初始化流程，新特性接进去 |

另一个代价在虚拟化上。虚拟机访问一个由软件模拟出来的设备时，每次读写寄存器都要陷入宿主机处理，比访问真实设备又慢很多。让虚拟机直接使用真实设备，以及专门为虚拟机设计的设备接口，都是为了绕开这个代价。

## 补充

主线到上面结束。下面是遇到时需要知道的三个变体。

**有意放宽的映射：write-combining。** 设备里有些区域其实只是一块存储，读写它不会让设备做别的事，典型的是显存。向它逐次写小块数据太慢，于是有一种专门的映射方式：CPU 把连续的写攒起来，凑满一批一次发出。代价是放弃了 Device 类型的保证，写可能被合并、重排、延迟。Arm64 上 Linux 的这种映射用的是"不经 cache 的 Normal 类型"。它只能用在确认读写没有额外效果的区域：PCIe 设备会在 BAR 里用"可预取"标志声明这一点，片上设备没有这种标志，要驱动作者自己清楚。

**PCIe 设备的配置信息也用 MMIO 访问。** 每个 PCIe 设备有一块 4 KB 的配置空间，放着设备的身份信息和 BAR。它不在第 2 节说的窗口里。主桥另外提供一段地址，把所有设备的配置空间排在一起，软件按"起始地址 + 设备编号 × 4 KB"读写，主桥收到后发出的是配置报文。这套做法叫 ECAM（Enhanced Configuration Access Mechanism）。

**x86 的不同之处。** 思路相同，有三点差别。第一，x86 除了 MMIO 还有一个独立的 64 KB 的 I/O 地址空间，用 `in` / `out` 指令访问，老式设备还在用；Arm 没有。第二，内存类型的名字不同：WB（可缓存）对应 Normal，UC（不可缓存）对应 Device，WC 对应 write-combining。第三，x86 对应系统寄存器的是 MSR（Model Specific Register）和控制寄存器。另外，x86 硬件对访问顺序的保证本身比 Arm 强，只在 x86 上测过的驱动拿到 Arm 上才暴露顺序问题，原因常在这里。

## 和其他主题的关系

- **内存顺序与屏障（路线图第 2 项）。** 本文只保证了同一设备内部的访问顺序。"先把数据写进内存，再写寄存器通知设备"这种跨内存和设备的顺序，要靠屏障。
- **设备发现（第 9 项）。** 第 2 节的地图从哪来：设备树、ACPI、PCIe 扫描和 BAR 分配。
- **DMA 与 IOMMU（第 11 项）。** 本文是 CPU 访问设备。反方向是设备访问内存。
- **描述符环 + doorbell（第 12 项）。** doorbell 就是一次 MMIO 写，它什么时候到达设备，由本文第 5 节决定。
- **AI Infra。** GPU 的控制寄存器和显存是 BAR 里的两类区域，前者用 Device 类型映射，后者用 write-combining。CUDA 提交一批计算任务，最后一步是向 GPU 的 doorbell 寄存器做一次 MMIO 写。RDMA 网卡（NCCL 跨机通信底下用的那类）把 doorbell 所在的页直接映射给用户态进程，进程不进内核就能写设备寄存器，以此降低延迟。

## 依据与未核实

已对照 Linux v6.6 的 `Documentation/driver-api/device-io.rst`：

- 默认的设备寄存器映射不缓存、不提前执行、不重排、不重复、不合并，写可能是 posted 的。
- Arm64 上默认映射是 Device-nGnRE；write-combining 映射是不经 cache 的 Normal 类型。
- 确认写到达的通用方法是写后读一次；PCI 的内存写总是 posted 的。
- PCI 上标了"可预取"的区域通常可以用 write-combining 映射。

来自规范的通用知识，这次没有打开规范逐字核对：

- Arm ARM（DDI 0487）里 G / R / E 的精确定义、R 的保证范围、MMU 关闭时数据访问的类型。
- 片上互连的错误应答转成同步异常还是 SError。这本身由芯片实现决定。
- PCIe 读不到设备时返回全 1 还是报错。这取决于主桥的实现，具体平台要查主桥的文档。
