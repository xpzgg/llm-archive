# vLLM 核心概念

> 这组笔记按"当时真正卡住的问题"组织，问法保留了原话——它们标记的是最容易误解的位置。
> 只记稳定的设计思想与心智模型，不对照源码。

---

## 一、prefill 与 decode

### Q：什么是 prefill，什么是 decode？和 encoder/decoder 有什么关系？

**两者算法完全一样**——都是 causal attention、同一份权重，区别只在 query 的行数 M：

- prefill：M = prompt 长度
- decode：每请求 1 行，只能靠拼 batch 把 M 撑起来

所以 **prefill/decode 不是算法概念，是性能概念**。M 的这一个差异让硬件行为整个反转：

| | prefill | decode |
|---|---|---|
| 瓶颈 | compute-bound | memory-bound |
| 权重利用率 | 加载一次，算 N 个 token | 加载一次，只算 1 个 token |

decode 每步要读完整份权重 + 完整份 KV cache，却只产出 1 个 token，算术强度接近零，算力单元基本空转。**后续几乎所有工程都是从这一个差异长出来的**：continuous batching、PagedAttention、chunked prefill、PCP/DCP。

**与 encoder/decoder 的关系：命名撞车，是两条正交的轴。**

- **架构轴**：encoder-only（BERT）/ decoder-only（GPT、GLM）/ encoder-decoder（T5）
- **运行轴**：prefill / decode

**prefill ≠ encoder。** encoder 的 attention 是 bidirectional 的，因果性不存在，**所以**它才能并行；prefill 的 attention 仍然是 causal 的，它之所以能并行，**是因为 prompt 已经全部已知**，因果性由 mask 保留。

> encoder 的并行来自 attention 结构，prefill 的并行来自输入已知。

### Q：prefill 就是把 prompt 的 token 跑一遍 forward，把 KV 缓存下来，decode 复用这些 cache？

对，补三点：

1. **prefill 不只填 cache，它也产出第一个 token。** prompt 最后一个位置算出的结果就是第一个生成 token。所以 TTFT ≈ prefill 耗时，TPOT ≈ decode 耗时——两个 SLO 分别对应两个阶段。
2. **缓存能成立的根本原因是 causal 性。** 位置 j 的计算只依赖前缀 x₁..x_j，**追加 token 不会改变前面任何东西**。更准确说，K/V 是跨位置信息的唯一必要形式——后续位置需要前文的方式只有 attention 里的 k·v，不需要 hidden state 本身。
3. **decode 不是"复用"，是"追加 + 复用"。** 每步先用新 token 算出它自己的 K/V 写进 cache，再拿它的 q 去和 cache 里全部历史做 attention。KV 是 **append-only、单调增长**的。

收益量化：**每 token 的计算量从 O(N) 降到 O(1)**（没有 cache 就要重跑整个前缀）。代价是显存 + "每步仍要读 O(N) 的 KV"这个带宽开销——这正是 decode memory-bound 的来源。

**这条性质是 CP 可行性的基础**：每段 token 的 KV 只由它自己及前缀决定，所以可以按 token 切分计算。

## 二、调度

### Q：chunked prefill 是什么？是按 chunk 粒度算 prefill forward 吗？

是，但**关键不在"切"，在于切完之后能和 decode 混在同一步**——前者是手段，后者才是目的。

### Q：chunked prefill 是为了解决什么问题？

**prefill 把 decode 饿死。**

长 prompt 的 prefill 是原子的——必须在一步内算完，吃光这一步的 token 预算，同一步里 running 的 decode 全都排不进来，延迟出现尖刺。

注意不是"prefill 占资源太多"：**prefill 恰恰是算得又快又满的那个**（compute-bound，硬件利用率高），问题在**调度粒度**——请求最小只能整段调度，没有中间态。解法是时间片化：切成 chunk 分散到多步。

**光切还不够，顺序才是关键**：每步先满足 running 的 decode，剩余预算给 prefill chunk 搭车（piggyback）。没有这个顺序保证，chunk 开得再小 decode 也可能被挤掉。

代价：prefill 被拉成多步串行，自己的 TTFT 变差。

> 用首 token 延迟，换生成延迟的稳定。本质是"削峰填谷"——纯 decode 步的算力本来就闲置，prefill token 塞进去花的正是这份闲置算力。

### Q：一步（step）里引擎做哪三件事？

1. **Schedule** —— 决定这步跑哪些请求、各跑多少 token
2. **Forward** —— 跑模型、采样出每个请求的新 token
3. **Postprocess** —— 把结果搬回请求状态

第 3 步是**唯一会改变请求本身**的地方：

- **让请求"生长"**：新采样的 token 追加进请求的 token 列表（下一步要把它当输入喂回去）
- **判断生死**：EOS token / 长度上限 / stop string
- **回收资源**：请求结束，它占的 KV cache block 归还池子

一个设计细节：这三件事**不在同一个地方**。append 和基于 token 的判断在引擎主循环内（由调度器做）；detokenize 和 stop string 匹配在循环**之外**——因为 stop string 必须在**文本**上匹配，天然和 detokenize 绑在一起。而请求状态归调度器所有，所以"搬回状态"这一步由它来做。

背后是 vLLM V1 的核心原则：**引擎主循环要尽可能精简**，它的纯 CPU 开销直接决定吞吐上限。

### Q：调度器的抽象是什么？

调度器里**没有 prefill，也没有 decode**。每个请求在它眼里只是一对数字：

- 已经算到哪
- 总共要算到哪

每步做的事情就是**派 token 让前者追上后者**。prefill 和 decode 的区别在这个抽象里完全消失——只是"差距 32000"和"差距 1"的区别。

这个抽象还顺带覆盖了 prefix caching（差距可以从缓存直接缩短）和投机解码（一次派多个 token）——因为它们都是"追上目标"的不同实现方式。

## 三、KV cache 与分页

### Q：KV 管理器分配 block，是不是相当于页表分配页框？

对，这是最贴切的类比：

| vLLM | OS |
|---|---|
| 逻辑 block 号 | 虚拟页号 VPN |
| 物理 block 号 | 物理页框号 PFN |
| block table | 页表 |
| slot_id | 算好的物理地址 |

但有两处**根本差异**：

**1. 没有缺页机制。** OS 的物理页框在*访问那一刻*才分配，分不到就缺页、回收、OOM。vLLM 没有——一次 forward 是一整批发下去的计算，**所有 token 的 KV slot 必须在启动前就有效**，中间没法停下来要一块显存。

于是分配必须在**调度时刻**完成且成功：装不下就不调度这个请求（排队），或者去抢占别的请求。

> **结论：block 分配是调度决策，不是运行时机制。** 这也是 KV 管理器为什么和调度器放在一起，而不是放在设备侧。

**2. 没有"便宜的缺页"。** OS 换页代价尚可容忍且对程序透明；vLLM 装不下时只能重算（丢 block 后重新 prefill）或换出（KV 挪到 host），代价高一个量级，而且请求会被真的踢出这一步的 batch——客户端看到的是延迟抖动。

（结构上还有一处：OS 用多级页表是因为地址空间巨大且稀疏；一个请求的序列是 `0..N-1` 的**稠密连续区间**，没有空洞，扁平数组反而更省更简单。）

### Q：block table 里存的是什么？key 是 token id 吗？

**key 不是 token id。** 两个轴分别是"哪个请求"和"第几块"：

| | 含义 |
|---|---|
| 行 | 请求在 batch 里的**槽位**（不是请求 id） |
| 列 | 该请求的**第几个逻辑块** |
| 值 | 那一块实际落在**哪个物理 block** |

例：一个 100 token 的请求，每块装 16 个 token → 需要 7 个逻辑块（0-15、16-31、…、96-99，最后一块只填了 4 个）。假设它占槽位 2，第 2 行大概是：

```
[ 12, 45, 7, 88, 3, 91, 20, 0, 0, 0, … ]
   ↑                                    ↑
 逻辑块0 → 物理块12              后面的 0 是没用的
```

读法：**这个请求的第 0 段序列存在物理块 12，第 1 段在物理块 45，第 6 段在物理块 20。**

三个容易卡住的点：

- **行是槽位，不是请求 id**——它不是"按 id 查的表"，而是按槽位直接索引的稠密数组（O(1) 下标寻址，不是哈希表）
- **值为什么是物理块号而不是最终地址**——这张表只做**逻辑↔物理的映射**，地址换算在下一步
- **逻辑块号本身也不存在任何地方**——它是 `position // 每块 token 数` 现算的，用完就丢；被存下来的只有物理块号

### Q：token id 和 position 是一回事吗？

**不是，这是最容易混的一处。**

- **token id**：这个词是词表里的第几个词 —— 描述**这个词是什么**
- **position**：这个 token 排在序列的第几位（全局、从 0 起，跨 prompt 和已生成部分连续编号）—— 描述**它在哪儿**

同一个 token id 可以出现在任何 position；两个完全不同的 token id 也可以占据相邻的 position。

**block table 和 slot_mapping 全程只跟 position 打交道，从来不碰 token id。**

### Q：逻辑 block 是 chunk 的粒度吗？

不是，两个不同的切法：

| | block | chunk |
|---|---|---|
| 划分的是 | **存储 / 地址空间** | **一次调度推进的计算量** |
| 大小 | 固定（每块若干 token） | 每步可变，取决于剩余 token 预算 |
| 谁定 | 启动时定死 | 调度器每步现算 |
| 目的 | 分页管理 KV cache | 让长 prefill 交错进 decode |

> **block 是"存哪儿"的划分，chunk 是"这次算多少"的划分。**

**两者不需要对齐**：一个 chunk 可以横跨很多 block，也可以小到装不满一块。它们靠 position 接上——chunk 决定"这次算哪些 token"，block 决定"算出来的 KV 存到哪儿"。**chunk 是动的，block 是静的。**

### Q：一个物理 block 里装的是什么？

**每块 token 数量那么多 token 的全部 KV**：

- 跨**所有 layer**
- 每层的**所有 head**
- **K 和 V**

所以它的字节数 = 每块 token 数 × 每 token 每层 KV 字节数（head 数 × head_dim × 数据宽度，K 和 V 各一份）× 层数。

三个精度：

1. **block 号是"跨层的索引"，不是一段跨层的连续内存。** 物理上每层是各自的张量，block `m` 的含义是"每一层张量里的第 m 片"。
2. **方向很重要**：是先有 token 粒度，再由它推出每块的字节数，最后才 `块数 = 可用显存 // 块字节数`。不是"块大小定死、再问 token 装不装得下"。
3. 规格相同的层会归成一个 **KV cache group**，共用一张 block table（所以可以有多张 block table）。

（MLA 系模型存的是压缩后的 latent 而不是完整 K/V，每 token 的这个值小得多。）

### Q：物理块里存的是不是 token 到 slot 的映射？

**不是。物理块是存储，不是映射。** 它里面装的就是 KV 数值本身，没有任何 id、没有映射表。

三种东西别混：

| | 存什么 | 性质 |
|---|---|---|
| **物理 block** | KV 数值（K/V 向量） | 存储 |
| **block table** | 逻辑块号 → 物理块号 | 映射 |
| **slot_mapping** | 本步每个待算 token → 它的 slot | 每步算出来的中间结果 |

### Q：position 是什么？怎么从它找到 KV？

**position 就是这个 token 在整条序列里排第几**，从 0 开始数。是绝对的——不是"这一步的第几个"，也不是"这个 chunk 里的第几个"。它和喂给模型做位置编码的那个量是同一个。

寻找路径（`//` 是整除，只取商的整数部分）：

```
position                                          ← 入口：这个 token 排第几
  → // 每块 token 数                               → 逻辑块号
  → block_table[槽位, 逻辑块号]                     → 物理块号
  → 物理块号 × 每块 token 数 + position % 每块 token 数  → slot_id
  → 用 slot_id 索引 KV cache                        → 读到 K/V 数值
```

**入口是 position，出口是 KV 数值。**

整除为什么能得到块号：block 把序列切成等长连续的区间，整除就是在问"这个数落在第几个区间里"。

```
position // 每块 token 数  →  第几块     （类比：地址 // 页大小 → 页号）
position %  每块 token 数  →  块内偏移   （类比：地址 %  页大小 → 页内偏移）
```

和地址翻译那套位运算是同一个东西，这里换成了除法取余。

**一个关键精度：slot_id 不是字节地址。** 它是 KV cache 里的第几个 token 槽；字节地址还要再乘"每槽字节数"，那一步由框架和 kernel 完成。

这也解释了**为什么 kernel 拿到的是 slot_mapping 而不是字节指针**：位置是唯一每步会变的信息，而基址、步长、层布局都在启动时就固定、编进 kernel 参数了。

> 不是"位置自包含全部信息"，而是**位置是唯一会变的那部分信息**。

### Q：prefix caching 怎么知道前缀能复用？

**匹配的不是 prompt 文本，是每块的内容哈希**，而且哈希是**链式**的：

```
本块的哈希 = hash(前一块的哈希, 本块的 token ids, extra keys)
```

**为什么必须链式**：KV 是上下文相关的——同样一段 token，前面接的内容不同，算出来的 KV 就不同。所以第 100 块的 KV 能不能复用，前提是第 0..99 块全部对得上。链式哈希天然保证"哈希对上 ⟹ 前缀全对上"；只按单块内容做哈希会产生"内容一样但前缀不同"的误命中，结果直接算错。

匹配过程：逐块查表，命中就复用（引用计数 +1），**遇到第一个不命中就停**，从那儿往后老老实实算——这就是"最长前缀匹配"。只有满块参与，末尾没填满的块不算、不可共享。

**它服务的主要是 agent 场景**：harness 每轮把整个对话重发成新请求，前缀极长，靠它避免重算。

## 四、执行分层

### Q：Worker 和 ModelRunner 的职责分别是什么？是 Worker 接入调度层、Runner 完成具体任务吗？

方向对，但"接入调度层"那一步是**执行器**的活（它负责把一步扇出到所有 rank）。分层是：

```
引擎主循环
  → 一份调度清单
  → 执行器          跨 rank 扇出
      → Worker[rank]
          → ModelRunner   ← 真正干活
```

- **Worker** —— 一个 rank（一台设备）的资源与生命周期所有者，也是引擎唯一认识的接口：对外**声明**这台设备有什么，对内持有设备态、把每步计算转发给 runner。
- **ModelRunner** —— Worker 内部的运行时，持有请求态，把调度清单从**请求空间**翻译成**张量空间**并完成每步执行。

**判据（生命周期轴）**：凡是"每 rank 一次、跨整个服务生命周期只做一次、且决定这台设备上有什么"的事，归 Worker；凡是"每步一次"的事，归 ModelRunner。

Worker 那几件事各自带着**不可逆的顺序约束**（这正是它构成流水线的原因），两条值得记住：

- 分布式环境必须在内存快照**之前**（通信 buffer 先分配，否则会被算成可用显存）
- KV cache 必须在图捕获**之前**（捕获要用真实张量）

**功能轴**：

| 轴 | Worker | ModelRunner |
|---|---|---|
| 资源 ↔ 计算 | 拥有物理资源：设备、通信组、显存池、权重副本、计算图 | 消耗这些资源做计算 |
| 容量 ↔ 实例 | 钉死**上限**：多少 block、多大批 | 在上限内决定**这一次具体是什么** |
| 接口 ↔ 实现 | 引擎唯一认识的类型 | 对引擎完全不可见 |
| 设备态 ↔ 请求态 | 设备世界的状态 | 请求世界的状态（请求表、block 表、采样参数） |

> 两条轴指向同一件事：**Worker 定义这台设备对外承诺什么，ModelRunner 负责兑现它。**

一个关键交接点：Worker 测出可用显存返回给引擎，引擎据此算出**总块数**再传回来——**这是 Worker 和调度器之间最关键的交接**：Worker 决定"有多少 block"，调度器在这个上限内做调度。

### Q："请求空间翻译成张量空间"怎么理解？

**请求空间**是调度器说的语言，纯逻辑、设备无关：

> 请求 A 这步算 512 个 token；请求 B 这步算 1 个；A 的 KV 存在 block 3、7、12。

只有请求身份和数量，没有形状、没有位置。

**张量空间**是计算单元说的语言，是布局、是"摆好的数据"：

> 全部 token 拼成一个连续张量；每个请求的 query 落在哪一段；每个 token 的 KV 该写哪个 slot。

计算单元不认识"请求"这个概念，它只认"一段连续的数，算完写回去"。

**为什么必须有人翻译**：

1. kernel 不认识"请求"
2. **调度是设备无关的，计算是设备相关的**——同一份清单在 1 张卡和 8 张卡上摆出来的形状不同。**这就是 Worker/ModelRunner 必须每 rank 一份的根本原因**
3. 翻译里含了调度层不该操心的决定：batch 怎么拼、padding 到多少、slot 怎么排

类比：**VFS 说"往这个文件的偏移 8192 写 4KB"，块层说"把这段搬到 12345 号扇区开始的 8 个扇区"。** 前者语义视图，后者布局视图，翻译由文件系统完成。

（注意分界：**Worker 是这条信息的转发者，不是提出者。** "算哪些 token"是调度器说的。）

### Q：为什么"batch"有两份？

同一批请求有两个视图，各由一层负责：

| | 调度器那份（逻辑 batch） | Runner 那份（物理 batch） |
|---|---|---|
| 内容 | 哪些请求这步跑、各跑多少 token | 承载它们的设备端工作集：缓冲区、槽位、block 表、采样参数 |
| 性质 | 设备无关、语义的 | 每设备一份、布局的 |
| 形式 | 一份清单 | 持久结构，每步原地更新 |

佐证：请求结束时**两边都要清一遍**——postprocess 里调度器标记结束并归还 block，runner 那边把它从持久 batch 移除。同一件事清两次，说明确实有两份状态。

物理 batch 之所以必须**持久、预分配、形状固定**，是为了支持计算图捕获（形状会变就没法录）。这是纯设备侧约束，不该污染调度器。
