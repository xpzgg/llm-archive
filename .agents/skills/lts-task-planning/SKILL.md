# LTS 回合任务分配

把补丁组织成可并行分配的任务包，减少重复适配和交叉等待。重点回答哪些补丁应由同一人处理、按什么顺序，以及为什么。

## 分析依据

可用主线仓库 `/home/yjc/project/linux`、stable 仓库 `/home/yjc/project/stable`，或社区发布邮件、提交页面；按需要 fetch 或用 b4 获取邮件，自行选择高效方式。以用户给定清单或发布范围为准，明确实际核对的版本、批次。

结合提交说明、diff 和历史判断关系，关注 `Stable-dep-of`、`Fixes`、接口变化及重叠修改。区分语义依赖、补丁上下文依赖和仅因改动相关而建议同人处理；同文件或提交相邻本身不证明依赖。

按对应 stable 分支核对顺序，不直接套用主线时间线。跨版本的同源修复可交给同一负责人，但分别列出各版本的提交和前提。引入改动及其回归修复应配套交付。发现清单外的关键前置或后续修复时，单独指出与任务包的关系。

默认基于公开代码规划；内部仓不可用不妨碍分组，但不能据此断言内部版本已合入、缺补丁或能无冲突应用。仅在用户要求且提供目标代码时扩展到内部依赖核对。本技能的交付是分配方案，实际回合按用户另行指定的范围执行。

## 交付：每组一段，可直接粘贴到任务网站

覆盖全部输入补丁，每个任务包给一份简短说明，不逐 commit 重复输出备注。标题明确标注内核版本，随后列出 commit、标题及推荐处理顺序，再用一小段解释关联和拆开或倒序处理的影响。例如：

```text
A 包：platform（Linux 5.10），按以下顺序处理

<commit>  <标题>
 → <commit>  <标题>
 → <commit>  <标题>

<简述前后改动的关系，为什么建议同一人按此顺序处理。>
```

同一包涉及多个版本时，分别标注版本并列出各自的补丁顺序，共用关联说明；不同版本之间不连依赖箭头。无顺序要求的补丁直接标明可独立或并行处理。

对有前置关系的组，统一提醒：前置计划合入但尚未合入时，先等待并在合入后更新基线，避免重复适配；同一负责人可在包含前置的补丁栈上连续处理，按顺序合入。仅因同模块建议同人处理，不设置等待门槛。必要的配套交付、跨包等待、清单外前置和证据链接放在组说明中，内部合入状态未知时不作断言。

有人员数量或专长信息就据此分配，否则用任务包或负责人代号，不按补丁数量机械均分。不展开逐补丁根因教程或未经验证的工时估算。
