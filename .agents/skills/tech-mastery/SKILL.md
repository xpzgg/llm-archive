# Tech Mastery：把一项技术讲到目标等级

## 这份材料为谁、为什么

读者是用户本人。他的注意力有限，读这份材料是为了在工作里用上：听懂设计讨论、读懂代码、定位问题，或者判断改动的影响、参与社区。所以衡量材料只有一个标准：读完之后，他能不能回答目标等级的问题。覆盖了多少方面、分了多少节都不算数；如果删掉某一节，读者并不会少懂什么，那一节就不该占篇幅。

## 三个等级：读完要能回答什么

**L1 概念与设计：“它是什么，为什么这样设计”**
讲为什么要有它，它解决什么问题、核心思想是什么、由哪几部分组成、各部分负责什么、一次典型处理怎样在这些部分之间流转，以及关键取舍（得到了什么、付出了什么）。不涉及代码。
读完后：能讲给同事听，在设计讨论里跟得上。

**L2 实现：“它在代码里是怎么做到的”**
讲关键数据结构和状态、关键代码路径、并发和边界情况，以及怎么正确使用、出了问题怎么调试。
读完后：能读懂和修改代码，能从故障现象定位到原因。

**L3 视野：“它在更大的系统和时间线里处在什么位置”**

* 空间上：和上下游、相邻模块怎么配合，谁依赖它、它依赖谁，组合使用时有哪些边界。
* 时间上：为什么演进成现在这样，每次大改的动因是什么，哪些方案被放弃了，社区正在往哪个方向走。

读完后：能判断一个改动会影响到哪里，能评审补丁，能在社区讨论里提方向。

等级是累加的：L2 以 L1 为前提，L3 以 L2 为前提。等级不明确时，从用户的说法推断；推断不了就问。

## 怎么组织材料

围绕终点问题来组织，大部分篇幅留给一条主线。其他内容（术语、接口、变体、和已有知识的关系）只在能帮读者回答问题时才放进来，放在主线之后，篇幅要小。放哪些内容、怎么排、拆成几份，由你根据主题判断，没有固定的章节模板。

每个等级的主线通常是下面这样。它们是起点，不是必须照搬的结构。

**L1**：先讲为什么需要它，也就是没有它会怎样；再讲为什么要这样解，设计压力在哪里；然后讲它由哪几部分组成，一次典型处理怎样在这些部分之间流转；最后讲付出了什么代价。读者带着问题看机制，才知道每个部分为什么存在。

**L2**：沿着 L1 的那条处理流程往下，一直走到代码里。按机制来组织，每个机制讲清它用什么数据结构、管理哪些状态、状态在哪一步怎么变；接着讲并发和边界情况、怎么正确使用、出了问题从什么现象查起。不要按时间顺序罗列函数，那样会写成流水账，看不出设计。

关键处理路径要画成调用图：一个请求从入口进来，经过哪些层和关键函数，最后落到哪里，并标出状态在哪一步改变。用官方 anthropic-skills:excalidraw-diagram skill 画。用户试过 Markdown 函数索引，觉得不好用。

**L3**：以“一个改动会影响到哪里”为线索。

- **空间上**：画出它和上下游的交互面：它调用谁，谁通过什么钩子调用它，和相邻模块组合使用时边界在哪里。改动的影响就是沿着这些交互面传出去的。
- **时间上**：讲每次大改的动因，以及被放弃的方案。不要按年份罗列提交，历史的价值在于解释现在的设计为什么是这样。
- **收尾**：落到社区正在往哪个方向走，还有哪些问题悬而未决。

历史和版本都要用 git 核实，方法见“事实核实”。

下面是对所有等级都适用的写法。它们都来自同一个事实：理解是读者在脑子里搭起一个因果模型，而读者的注意力有限。每条都附了理由，方便你遇到新情况时自己推断：

- **先给问题，再给答案。** 读者手里有了问题，后面的每条信息才有地方挂；没有问题，机制就只是一堆需要硬记的事实。
- **先给全貌，再进细节。** 讲任何一部分之前，先让读者知道它在整体里的位置。没有全貌，读者就无法判断眼前的细节有多重要。
- **每一步只依赖已经讲过的东西。** 概念、术语、前提，都要先建立再使用。读者一旦碰到还没讲过的东西，就只能卡住或者跳过，后面的理解跟着断掉。
- **讲清因果，不要罗列。** 每个部分都要说明它为什么存在、和其他部分怎么连接。一串互不相连的事实很难记住，也没法用来推理；一条因果链能让读者推出没写出来的东西。
- **用一个具体例子把机制跑一遍，一直跑到结果。** 抽象描述容易被读者误解成别的意思，一个跑通的例子能当场检验理解对不对。只开头不收尾的例子，读者看不到机制起了什么作用。
- **每个名字都要值得读者记住。** 新名字会占用注意力，所以只引入回答问题真正需要的名字；其余的说它的作用就够了。
- **篇幅和位置跟着重要性走。** 读者默认越大、越靠前的内容越重要。如果主次和篇幅不一致，读者就会把精力花在次要内容上。
- **把确定的和不确定的分开。** 未核实的内容要标出来，否则读者会把猜测当事实用。但标注要放在不打断主线的位置。
- **用读者已经懂的东西来对接新概念，并且只用准确的对应关系。** 新知识挂在已有知识上最牢。不准确的类比会把原概念的特性一起带过来，读者就会推出错误的结论。

下面是以前实际出过的问题，要避免：

- 把一份要素清单逐项做成同等分量的章节，结果主线被挤到角落。例如 2026-10 的 MPAM L1 图，真正回答“是什么、为什么、怎么解决”的只占三分之一。
- 术语表、命令框占的面积比机制讲解还大。
- 在“问题”部分就用上后面才引入的概念，比如还没讲到 MPAM 就出现了 PARTID。
- 只按时间顺序列函数，不讲设计。
- 大段的待核实说明压在主路径上。

## 协作流程

1. **对齐。** 确认目标等级、读者已经知道什么、交付物放在哪里、用什么形式；说明主线打算怎么讲，得到用户确认后再动手。大部分返工都来自跳过这一步。
2. **研究。** 以一手资料为准，并固定版本（见下文“事实核实”）。
3. **先做样板。** 篇幅大或者形式新时，先完成一个单元给用户看，方向确认后再铺开。
4. **产出。** 画图交给官方 anthropic-skills:excalidraw-diagram skill，按它的规则输出和检查，包括要不要渲染。
5. **交付前读一遍。** 以目标读者的身份把材料读一遍：能不能回答终点问题？逐节问自己：删掉这一节，读者会少懂什么？
6. **交付。** 按仓库的目录约定放好，文件之间互相链接，注明依据的版本。如果发现旧笔记里有过时或错误的内容，先告诉用户，不要擅自修改。

长时间研究或作图时，主动简短汇报进展。

## 事实核实（技术主题通用，git 仓库尤其要注意）

- **固定版本。** 用 `git show <tag>:path` 读指定版本的文件，不依赖工作区的检出状态：工作区可能是旧版本或者有本地修改，也不要随意切换分支。
- **git 历史查询一律带上版本**，写成 `git log <tag> ...`。不带版本就默认从 HEAD 查，而 HEAD 如果是旧版本，会漏掉新提交。
- **“功能何时出现”不等于“文件何时出现”。** 文件经常被拆分重组。查功能要用 `git log <tag> -S <symbol> -- <file>` 或 `--grep`，找最早的那个提交，再用 `git describe --contains <commit>` 得到它首次合入的版本。
- **zsh 里要写成 `"${T}:path"`。** 写成 `$T:t…` 或 `$T:l…` 会被 zsh 当成路径修饰符改写，导致 `git show` 找不到文件。
- **名字会改。** 函数、字段、配置项跨版本改名很常见，比如 `dyntick` 改成了 `rcu_watching`。旧笔记和网上资料里的名字，要用当前版本核对一遍。
- **社区信息以仓库文件为准。** 维护者、邮件列表、开发分支看 MAINTAINERS 之类的文件，不要凭记忆。
