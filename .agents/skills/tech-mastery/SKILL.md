# Tech Mastery：把一项技术讲到目标等级

## 这份材料为谁、为什么

读者是用户本人，一位芯片公司的内核负责人，正在向 AI Infra 拓展。他的注意力有限，读这份材料是为了在工作里用上：听懂设计讨论、读懂代码、定位问题、判断改动的影响、参与社区。

衡量材料只有一个标准：读完之后，他能不能回答目标等级的问题。篇幅花在对的地方：花在回答这些问题必须弄懂的内容上；辅助内容够用就行。

## 三个等级：读完要能回答什么

**L1 概念与设计：“它是什么，为什么这样设计”**
为什么要有它、它解决什么问题、核心思想是什么、由哪几部分组成、各部分负责什么、一次典型处理怎样在这些部分之间流转、关键取舍（得到了什么、付出了什么）。停在概念和设计层面，代码留给 L2。
读完后：能讲给同事听，在设计讨论里跟得上。

**L2 实现：“它在代码里是怎么做到的”**
关键数据结构和状态、关键代码路径、并发和边界情况、怎么正确使用、出了问题怎么调试。
读完后：能读懂和修改代码，能从故障现象定位到原因。

**L3 视野：“它在更大的系统和时间线里处在什么位置”**
* 空间上：和上下游、相邻模块怎么配合，谁依赖它、它依赖谁，组合使用时边界在哪里。
* 时间上：为什么演进成现在这样，每次大改的动因，被放弃的方案，社区正在往哪个方向走。

读完后：能判断一个改动会影响到哪里，能评审补丁，能在社区讨论里提方向。

等级是累加的：L2 以 L1 为前提，L3 以 L2 为前提。等级不明确时，从用户的说法推断；推断不了就问。

## 读者是怎样理解一项技术的

材料的结构由你根据主题设计。设计时，跟着读者脑子里搭模型的顺序走：

1. **先感到问题。** 让他看到没有它时具体会坏在哪里。手里有了问题，后面每条信息才有地方挂。
2. **再看到它的样子。** 它做什么、由哪些部分组成、每部分管什么。硬件或有物理形态的东西，要让他看到它在芯片或系统里怎么摆、有几个实例、怎么连。有了全貌，他才能判断细节的轻重。
3. **再看它怎么运转。** 用一个具体例子把一次处理从头走到结果，出错的路径也走到。跑通的例子能当场检验理解。
4. **然后才追问为什么。** 他已经见过形状和运转，这时讲“为什么是这个形状”才有东西可对照。最有说服力的讲法通常是：拿掉某个部分，开头的哪个问题会回来；保留它，又怎样解决了这个问题。
5. **最后看代价。** 得到了什么、付出了什么、怎么缓解，以及缓解本身的代价。

这是理解发生的顺序，不是章节模板。主题不同，每一步的分量和表现形式都应该不同；有的步骤可以合并，有的要拆成好几块。按这个主题本身最清楚的方式组织，每次都从内容出发重新设计。

L2 沿着 L1 的那条处理流程往下走到代码里，按机制组织：每个机制用什么数据结构、管理哪些状态、状态在哪一步怎么变，然后是并发、边界、正确用法、从什么现象查起。关键处理路径画成调用图，让读者一眼看出请求从入口经过哪些层、落到哪里、状态在哪里改变。

L3 以“一个改动会影响到哪里”为线索：空间上画出它和上下游的交互面（它调用谁、谁通过什么钩子调用它），影响沿这些面传出去；时间上讲每次大改的动因和被放弃的方案，用历史解释现在的设计；最后落到社区的方向和悬而未决的问题。历史和版本用 git 核实。

## 好材料的样子

- **因果相连。** 每个部分都说明它为什么存在、和其他部分怎么连接。一条因果链能让读者推出没写出来的东西。
- **概念先建立再使用。** 每一步只依赖已经讲过的东西，术语在第一次出现时就给出含义。
- **主次一眼可见。** 越重要的内容越大、越靠前、占的面积越多；主线占大部分篇幅，术语、接口、变体等辅助内容放在主线之后，篇幅小。
- **名字精挑细选。** 只引入回答问题真正需要的名字，其余的说它的作用就够了。
- **标题是大白话。** 节标题直接说这一节回答什么问题，比如“为什么这样设计”“一次请求怎么走”，读者扫一眼就知道往哪看。
- **确定和不确定分开。** 未核实的内容标出来，标注放在主线旁边的脚注或附录里。
- **跟 AI Infra 挂钩。** 主题和 GPU、训练、推理、NCCL、CUDA、pinned memory 等有关联时，明确点出来。

## 画图

图的任务是让读者看见文字说不清的东西：结构的形状、请求的流向、状态的变化、前后的对比。画之前先想清楚这张图要让读者看懂什么，再为这个内容选最合适的视觉形式。不同的概念用不同的形式表达：层次用树、流程用泳道或时间线、对比用并排、构成用嵌套的框。

用官方 `anthropic-skills:excalidraw-diagram` skill 画，输出 `.excalidraw.md`，放进用户的 Obsidian 仓库。按它的规则写 JSON、做自检，自检通过就交付文件；用户要看渲染效果时再渲染。

几个和这个仓库相关的事实：
- 元素 id 用 8 位字母数字（如 `aB3x9QzK`）。Obsidian 的 `.md` 格式按 `^id` 切分文字，8 位 id 能让每段文字都对上自己的元素。
- Obsidian 打开过的图会被存成 `compressed-json`（LZString base64）。要修改时先解压成普通 `json` 块再编辑，插件下次保存时会重新压缩。
- Excalidraw 插件的 `zoomToFitOnOpen` 已关闭：图打开时停在文件里 `appState` 保存的视角（`zoom`、`scrollX`、`scrollY`）。新图可以设一个让第一屏宽度铺满、留有边距的初始视角。

**调用图的视觉语言**（用户认可、适用于任何代码库）：调用从左向右展开，扇出用弯曲的虚线，每个框上方一行说明，每条路径一个面板。框的颜色表示代码归谁：蓝 = 主体代码，黄 = 回调，绿 = 外部；虚线框 = 关键语句或数据，菱形 = 分支。线的颜色表示两个框的关系：深色 = 调用，橙 = 回调，紫 = 交给另一个执行者，红 = 数据从哪来。红色标出最要紧的地方。额外信息写进框上方的说明里，让这套语言保持简短好记。

## 协作流程

1. **对齐。** 确认目标等级、读者已经知道什么、交付物放在哪里、用什么形式；说明主线打算怎么讲，用户确认后再动手。
2. **研究。** 以一手资料为准，并固定版本（见“事实核实”）。
3. **先做样板。** 篇幅大或形式新时，先完成一个单元给用户看，方向确认后再铺开。
4. **产出。** 文字按上面的写法组织，图交给官方 excalidraw skill。
5. **交付前读一遍。** 以读者的身份读一遍：能回答终点问题吗？篇幅是不是花在了回答问题必须弄懂的内容上？
6. **交付。** 按仓库的目录约定放好，文件之间互相链接，注明依据的版本。旧笔记里发现过时或错误的内容，先告诉用户，由他决定怎么改。

长时间研究或作图时，主动简短汇报进展。

## 事实核实（技术主题通用，git 仓库尤其要注意）

- **固定版本。** 用 `git show <tag>:path` 读指定版本的文件，这样结果和工作区的检出状态无关。
- **git 历史查询带上版本**，写成 `git log <tag> ...`，这样能看到该版本之前的全部提交。
- **查功能何时出现，要查符号而不是文件。** 文件常被拆分重组，用 `git log <tag> -S <symbol> -- <file>` 或 `--grep` 找最早的提交，再用 `git describe --contains <commit>` 得到它首次合入的版本。
- **zsh 里写成 `"${T}:path"`**，让 zsh 把冒号原样传给 git。
- **名字以当前版本为准。** 函数、字段、配置项跨版本常改名（如 `dyntick` → `rcu_watching`），旧笔记和网上资料里的名字要用当前版本核对。
- **社区信息以仓库文件为准。** 维护者、邮件列表、开发分支看 MAINTAINERS 等文件。
